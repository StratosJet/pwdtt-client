# WDTT V3: проект общего UDP backend для DTLS/TURN путей

Статус: дизайн, **без изменений рабочего протокола или бинарников**. Базовая ревизия клиента: `846dec6d8dacb8ee385dc75c45f68882fc85c543`. Работающая V2 на `wdtt-gateway` и сервер `mk1` не изменяются.

## Задача

Девять DTLS/TURN воркеров одной логической WireGuard-сессии должны обслуживаться **одним** UDP backend-сокетом к серверному WireGuard. Это должно устранить переключение WG endpoint между девятью локальными портами, но не гарантирует устранения зафиксированных потерь downlink 30–40%.

## Проверено по исходникам (23.10.2026)

- `client/core/session.go`: после DTLS handshake вызывается `configGate.tryDeliver(...)` только при `needsConfig()`. Для сохранённой WG-конфигурации GETCONF может не отправляться. Затем воркер регистрируется в `Dispatcher`, читает DTLS и доставляет данные через `deliverReturn`.
- `client/core/dispatcher.go`: WG return-очередь блокирует отправителя при заполнении, отдельная drop-on-full ветка относится к RAW chunked.
- **Публичный**, но не гарантированно совпадающий с установленным на mk1, `ildarmaga/wdtt/server/server_conn.go`: `handleConn` выполняет DTLS handshake, опционально GETCONF/READY, затем `net.Dial("udp", wgEndpoint)` на отдельное соединение. Для случая без GETCONF определяет устройство по WireGuard и/или локальному UDP-порту.
- Установленный на mk1 бинарник имеет другую/модифицированную ревизию; он не служит надёжной сборочной основой V3 без получения точных исходников.

## Предлагаемый протокол V3 (пока НЕ реализован)

После DTLS handshake, **до первого WireGuard-пакета**, каждый V3 воркер посылает контрольный кадр с явным version/type и параметрами:
- `tunnel_id`: 16 криптографически случайных байт на запуск логического туннеля; общий для его девяти воркеров
- `stream_id`: слот 0..8 (номер пути не является секретом)
- `device_id`: идентификатор устройства в существующей модели авторизации
- `join_nonce`: уникальное значение на попытку регистрации
- `auth`: способ доказательства полномочий, **подлежит аудиту существующей WRAP/GETCONF аутентификации до выбора формата**

Ответ `JOIN_OK` подтверждает привязку к логическому туннелю. До получения ответа клиент не передаёт обычные WG-датаграммы в этот DTLS-путь. `JOIN_DENIED` завершается закрытием пути. Старый сервер не обязан понимать JOIN; V3 допускается запускать только при явной настройке V3 endpoint. **Нет молчаливого fallback с отправкой V3 JOIN на V2 mk1.**

### Инварианты безопасности

1. Один TunnelID НЕ служит самостоятельным полномочием. Ключ сессии образован идентификатором аутентифицированного субъекта, устройством и TunnelID; устройства не могут присоединиться к чужому туннелю.
2. Создание UDP backend происходит только после успешной проверки авторизации и лимитов устройства. Все девять путей одной сессии используют этот backend, но независимые туннели имеют отдельные backend-сокеты.
3. Дубликат `stream_id` допускает контролируемую замену только внутри того же аутентифицированного туннеля; старый воркер при закрытии не может удалить новый (generation token).
4. `userSessionEnter` и учёт трафика требуют адаптации с per-connection на per-logical-tunnel: нельзя девятикратно считать одну сессию, нельзя обходить лимиты.
5. Нужны ограничения общего числа сессий, памяти, времени до JOIN, числа путей на сессию и grace-периода после потери последнего воркера. Конкретные значения устанавливаются тестами, не берутся наугад.
6. Контрольные кадры V3 никогда не передаются в WireGuard backend. Отказ регистрации закрывает путь.

## Серверная модель

`SessionManager` (ключ: аутентифицированный субъект + DeviceID + TunnelID) владеет `LogicalTunnel`.

`LogicalTunnel` владеет ровно одним `net.UDPConn`, одним reader-loop backend→DTLS, девятью независимо живущими `StreamSlot`, sticky-selected downlink slot, счётчиками и контролем завершения.

Uplink: каждый DTLS воркер передаёт полезные WireGuard-датаграммы в общий backend. Порядок поступления из разных DTLS-путей может нарушаться.

Downlink v3.0: один выбранный здоровый DTLS stream. Failover при завершении/ошибках, без побайтового round-robin. `DTLS.Write` может блокироваться: реализация должна предусматривать конечный deadline и не держать общую блокировку SessionManager во время I/O. Позже возможно изучение bonding/reorder в отдельной версии.

Необходимо явно определить реакцию на быстрое переподключение: backend НЕ пересоздаётся, пока туннель находится в ограниченном grace window. Последний воркер не имеет права освободить backend, если новая генерация уже активна.

## Наблюдаемость

На сервере: backend_write_attempt/success/error, backend_read_success/error, dtls_write_attempt/success/error, per-stream selection/switch, joined/rejected/evicted paths, очередь/задержка отправки.

На клиенте: TURN inbound, **реальные** queue-full drop counters (в используемом Pion v5.0.12), DTLS application datagrams, успешные/ошибочные UDP-записи в локальный WireGuard, queue wait.

Успешная запись в DTLS не равна доставке через VK TURN. Показатели двух машин сопоставлять только при синхронных измерениях.

## Порядок реализации и приёмка

1. Исследовать точные серверные точки аутентификации, `userSessionEnter`, `tryResolveConnFromWG` и WRAP identity; утвердить V3 JOIN auth и framing
2. Отдельный тестируемый пакет `sessionmanager`; unit tests для разделения устройств, девяти путей, duplicate stream ID, reconnect races, shutdown и grace
3. Добавить V3 handshake и явную feature flag на **отдельном сервере/порте**, без изменения работающего `wdtt.service` и `wdtt0`
4. Клиент V3 в отдельной экспериментальной ветке и бинарнике, без замены `/usr/local/bin/pwdtt-client`
5. `go test -race`, integration tests с отдельным тестовым WireGuard peer и последующая синхронная диагностика downlink на 1/3/5 Мбит/с

**Критерий архитектуры:** девять воркеров одного туннеля порождают один backend local UDP port, серверный WireGuard endpoint не прыгает при смене DTLS stream. **Критерий качества:** проверенная статистика потерь, не обещанная скорость.

## Запреты

Не менять mk1, wdtt.service, wdtt0, UFW, маршруты, watchdog, рабочий клиент и его бинарник без отдельного разрешения. Не использовать публичный серверный исходник как доказанно идентичный установленному бинарнику.
